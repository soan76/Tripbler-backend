# 공개 인증 API 요청 제한

인증 없이 열린 인증·가입 API의 남용과 인증코드 대입을 막는 규칙이다. 설계 배경은 `docs/superpowers/specs/2026-11-12-auth-rate-limit-design.md`에 있다.

## 전제
- 기록은 서버 메모리에 둔다. 서버 한 대 기준이며 재시작하면 초기화된다.
- IP는 접속 주소(`getRemoteAddr`)만 쓴다. 프록시가 없는 구성이라 `X-Forwarded-For`는 믿지 않는다. 프록시 뒤에 두거나 서버를 여러 대로 늘리면 이 문서와 구현을 다시 정해야 한다.
- 인증코드 오답 횟수는 DB(`attempt_count`)에 남으므로 재시작해도 유지된다.

## IP별 요청 제한
모든 한도는 "최근 N분" 기준이다. 허용 시각과 정확히 같은 시각의 요청은 통과한다.

| 묶음 | 경로 | 한도 |
| --- | --- | --- |
| 로그인 | `POST /api/v1/auth/login` | 1분 10번 |
| 메일 발송 | `POST /api/v1/auth/find-id/send-code`, `POST /api/v1/auth/password-reset/send-code` | 10분 5번(접수된 요청만 셈) |
| 복구·가입 | `POST /api/v1/auth/find-id/verify-code`, `POST /api/v1/auth/password-reset/verify-code`, `POST /api/v1/auth/password-reset`, `POST /api/v1/users`, `GET /api/v1/users/check-login-id` | 1분 30번 |
| 세션 | `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout` | 1분 60번 |

- 묶음끼리는 따로 센다. 로그인 한도에 걸려도 토큰 갱신은 된다.
- 요청 결과(성공·실패)와 상관없이 해당 경로에 도달한 요청을 센다.
- `HEAD` 요청은 `GET`과 같은 한도로 센다. Spring MVC는 `GET` 핸들러로 `HEAD`도 처리하므로, 따로 세지 않으면 `HEAD /api/v1/users/check-login-id`로 한도를 우회할 수 있다.

## 인증 메일 발송 제한
- 입력 이메일의 앞뒤 공백을 지우고 소문자로 바꾼 값으로 센다. 아이디 찾기와 비밀번호 재설정의 발송량을 합산한다.
- 같은 이메일은 마지막 발송 뒤 60초가 지나야 다시 보낼 수 있고, 최근 60분 동안 최대 5통이다.
- IP 한도와 이메일 한도를 함께 판정한다. 둘 다 허용될 때만 둘 다 센다. 한쪽 한도로 거절된 요청은 다른 쪽 횟수를 쓰지 않는다.
- 한도 안이면 가입 여부, 아이디·이메일 일치 여부, 메일 발송 성공 여부와 상관없이 `204`로 응답한다. 계정이 있는지 응답으로 드러나지 않게 하기 위해서다.
- 메일 발송이 실패하면 새 코드 발급을 롤백해 이전 코드를 그대로 쓸 수 있게 한다. 발송 한도는 차감된 채로 둔다. 실패는 서버 로그에만 남긴다.
- 알려진 한계: 메일을 요청 안에서 동기로 보내므로, 가입된 이메일은 응답이 더 느릴 수 있다(별도 과제).

## 이메일 입력 제한
- 아이디 찾기·비밀번호 재설정의 `send-code`, `verify-code` 네 경로는 `email`에 ASCII 인쇄 가능 문자(`0x21`~`0x7E`)만 받고 최대 254자까지 받는다. 어기면 기존 검증 오류 형식(`400 INVALID_REQUEST`)으로 응답하고 서비스는 호출하지 않는다.
- 이유: 제한기는 이메일을 Java 소문자 변환(`toLowerCase(Locale.ROOT)`)으로 묶어 세지만, 계정·인증코드 조회는 DB의 `upper(email) = upper(?)`로 같은 이메일을 판정한다. `ı`(U+0131), `ſ`(U+017F) 같은 문자는 소문자 변환에서는 그대로 남지만 DB 대문자 변환에서는 `I`, `S`가 될 수 있어, 피해자 이메일의 `i`·`s`를 바꾼 변형마다 제한기 키가 새로 생기면서도 같은 계정으로 메일이 나갔다(이메일당 한도 우회, 재발급마다 오답 5회 새로 확보). `@Email`은 로컬 부분에 비ASCII를 허용하므로 따로 막는다.
- 254자는 일반적인 이메일 주소 최대 길이다.

## 429 응답
한도를 넘으면 기존 오류 형식에 `Retry-After` 헤더(다시 시도할 수 있을 때까지 남은 초, 올림, 최소 1)를 붙인다. 여러 한도에 함께 걸리면 가장 긴 대기 시간을 준다.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 42
Content-Type: application/json

{ "timestamp": "...", "status": 429, "code": "TOO_MANY_REQUESTS", "message": "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요.", "path": "/api/v1/auth/login" }
```

- `TOO_MANY_REQUESTS`는 세션 만료 코드(`INVALID_REFRESH_TOKEN`, `EXPIRED_REFRESH_TOKEN`)와 다르다. 앱은 토큰 갱신이 429를 받아도 로그아웃하지 않는다.
- 429 응답마다 남기는 로그(`Rate limited: path=..., retryAfter=...`)는 `DEBUG` 수준이다. 공격 중에는 429가 대량으로 나서 `WARN`이면 로그가 폭증하기 때문이다. 키 상한 도달 경고는 그대로 `WARN`이다.
- 묶음별로 기억하는 키(IP·이메일)는 최대 10,000개다. 가득 차면 만료된 키부터 지우고, 그래도 가득이면 새 키의 요청을 429로 거절한다. 이때 `Retry-After`는 기존 키 중 가장 먼저 만료되는 키까지 남은 시간이다. 기존 키의 제한은 유지된다.

## 인증코드 오답 제한
- 같은 인증코드를 5번 틀리면 폐기한다. 폐기 뒤에는 정답도 거절한다. 새 코드를 요청하면 다시 쓸 수 있다.
- `verify-code`의 모든 실패(인증 레코드 없음, 이미 사용, 만료, 오답, 폐기, 비밀번호 재설정의 아이디·이메일 불일치)는 흐름별로 아래 코드 하나로 응답한다. 폐기된 뒤의 응답도 같다.

| 흐름 | 상태 | 코드 | 메시지 |
| --- | --- | --- | --- |
| 아이디 찾기 | 400 | `INVALID_FIND_ID_VERIFICATION_CODE` | 인증코드가 올바르지 않거나 만료되었습니다. 새 인증코드를 요청해 주세요. |
| 비밀번호 재설정 | 400 | `INVALID_PASSWORD_RESET_VERIFICATION_CODE` | 인증코드가 올바르지 않거나 만료되었습니다. 새 인증코드를 요청해 주세요. |

- 응답을 하나로 합치는 이유: 실패 종류(폐기·만료 등)가 응답에 드러나면, 인증 레코드가 있는지로 그 이메일이 연동 계정인지(재설정은 아이디와 이메일이 같은 계정인지) 알아낼 수 있다. 실패 종류는 서버 내부에서만 구분한다.
- 이전의 `*_VERIFICATION_ATTEMPTS_EXCEEDED`, `EXPIRED_*_VERIFICATION_CODE` 코드는 더 이상 쓰지 않는다.
- 이미 사용했거나 만료됐거나 폐기된 코드에 대한 요청은 오답 횟수를 올리지 않는다.
- 같은 코드에 대한 검증은 행 잠금으로 순서대로 처리한다. 다섯 번째 오답이 먼저 확정되면 뒤에 들어온 정답은 거절된다.
- 처리 시간 맞춤: 인증 레코드 없음, 이미 사용, 만료, 폐기로 거절할 때도 서비스 생성 때 한 번 만든 더미 해시로 해시 비교(`passwordEncoder.matches`)를 정확히 한 번 하고 거절한다. 오답과 같은 비교 비용을 거쳐, 응답 시간으로 인증 레코드가 있는지 알아내기 어렵게 하기 위해서다. 비교 결과는 쓰지 않으며 응답 코드와 횟수 처리는 위와 같다.
- 남은 한계: 오답일 때만 오답 횟수를 DB에 기록(쓰기)하므로, 그 차이만큼의 처리 시간 차이는 남는다. 실측은 하지 않았다.
