# 장소 API 호출 제한 설계

작성일: 2026-11-12 · 상태: 확정(사용자 승인)

표기: **(구현자 판단)**은 대화에서 정하지 않아 설계자가 정한 부분이다. 표시가 없는 부분은 사용자 결정이거나 사용자가 전달한 검토 의견을 반영한 것이다.

## 배경과 목적
- 장소 API는 요청마다 백엔드가 Google Places를 한 번씩 호출하고(유료), 서버 캐시와 호출 제한이 없다.
- 가장 걱정되는 상황: 한 사용자가 짧은 시간에 검색이나 상세 조회를 반복해 Google 호출량이 급증하는 것.
- 지켜야 할 흐름: 여행 중 여러 장소를 연달아 찾아보는 정상 사용은 막지 않는다.

### 현재 호출 흐름 (코드로 확인, 2026-11-12)
| 경로 | 인증 | 앱이 부르는 때 | 앱 쪽 중복 방지 | Google 호출 |
| --- | --- | --- | --- | --- |
| 검색 `GET /api/v1/places/search` | 로그인 필수 | 검색어 제출, 다시 시도 | 없음. 같은 검색어도 매번 나가고, 진행 중에 다시 제출해도 나간다(앞 응답만 무시) | 요청마다 1회 |
| 상세 `GET /api/v1/places/{placeId}` | 공개 | 검색 결과로 연 카드에서 "평점·영업 정보" 버튼 | 같은 장소 30분 앱 메모리 캐시(최대 50개), 조회 중 재요청 막음. 앱 재시작·로그아웃 시 비워짐 | 요청마다 1회(Enterprise 등급) |
| 주변 `GET /api/v1/places/nearby`, 최근접 `GET /api/v1/places/nearest` | 공개 | 부르지 않음(`loadNearbyPlaces`, `fetchNearestPlace` 호출처 없음) | — | 요청마다 1회 |

- 앱의 상세 요청(`PlaceApiService.fetchPlaceDetails`)은 지금 `Authorization` 헤더를 보내지 않는다.
- 상세 카드는 검색 결과를 골랐을 때만 열린다(`MapProvider.selectSearchResult`). 다른 진입 경로(`selectPlace`)는 호출처가 없다.

## 원칙
- 한도를 넘은 요청은 `429 TOO_MANY_REQUESTS` + `Retry-After`로 응답하고, **그 요청으로 Google 클라이언트를 호출한 횟수는 0회**여야 한다. (완료 조건)
- 아래 숫자는 모두 **개발 초기 설정값**이며 운영 보장값이 아니다.
- 사용자별 제한은 프로젝트 전체 비용 상한과 별개다. 전체 비용 상한은 Google Cloud 콘솔의 Places API 쿼터와 예산 알림으로 둔다(범위 밖, 콘솔 작업).
- **서버 결과 캐시는 두지 않는다.**
- 앱의 30분 상세 캐시는 프로젝트에 적용되는 Google Maps Platform 약관에 맞는지 별도로 검토한다. 앱 메모리에만 둔다는 사실만으로 허용 여부를 판단하기 어렵기 때문이다. 이번 범위에서는 바꾸지 않는다.

## 1. 검색
- 인증: 지금처럼 로그인 필수.
- 제한: 사용자별(JWT `sub`) **1분 10회, 1시간 100회**.
- 두 창(1분, 1시간)은 함께 판정하고, 둘 다 허용될 때만 둘 다 기록한다(기존 `AuthRateLimiter`의 원자적 판정과 같은 방식). 둘 다 걸리면 `Retry-After`는 긴 쪽이다.
- 입력 검증 실패(400)는 한도를 차감하지 않는다 **(구현자 판단)**: 검증을 통과한 요청만 서비스에서 센다.

## 2. 상세
- 인증: **로그인 필수로 바꾼다.** 토큰이 없거나 만료되면 401이며 Google 호출은 0회다.
- 제한: 사용자별(JWT `sub`) **1분 20회, 1시간 200회 (구현자 판단, 초기값)**. 검색과 따로 센다.
- 이유: 상세 카드는 로그인이 필요한 검색 결과에서만 열리므로, 비로그인 상세 조회를 제공할 이유가 없다. 공개로 두면 IP 제한밖에 없고, 공용 와이파이에서는 여러 여행자가 한도를 나눠 쓴다.

## 3. 주변·최근접
앱이 쓰지 않고, 유지할 외부 이용자도 없다. 사용자 결정(2026-11-12)으로 둘을 다르게 처리한다.

**주변 조회 `GET /api/v1/places/nearby`: 코드는 남기고 외부 접근만 막는다.**
- `SecurityConfig`에서 이 경로를 `denyAll()`로 막는다. 컨트롤러·서비스·클라이언트 코드와 그 테스트는 남긴다.
- 다시 열 때는 로그인만이 아니라 사용자별 호출 제한도 함께 둔다(로그인만으로는 계정 하나의 호출 수가 제한되지 않는다). 이 내용을 막는 설정 옆 주석에 적는다.
- 응답: 토큰이 없으면 401, 토큰이 있어도 403(`denyAll`). 어느 쪽이든 Google 호출 0회.

**최근접 조회 `GET /api/v1/places/nearest`: 삭제한다.**
- 컨트롤러의 엔드포인트, `PlaceService.findNearestPlace`, `PlaceClient.findNearestPlace`와 구현(`GooglePlacesClient`의 최근접 선택·거리 계산, 최근접만 쓰는 유형 없는 주변 검색 경로 등)을 지운다. 주변 조회가 함께 쓰는 코드는 남긴다.
- 최근접만 다루는 테스트와 `docs/places-api.md`의 "최근접 장소" 절, README의 경로 표기를 지운다.
- 주의: 상세 경로 `/api/v1/places/{placeId}`에는 `placeId` 형식 검사가 없다. 최근접 매핑만 지우면 `/api/v1/places/nearest`가 장소 ID `nearest`의 상세 조회로 해석되어 Google을 호출하게 된다.
- 그래서 `SecurityConfig`에서 `/api/v1/places/nearest`도 `denyAll()`로 막는다 **(구현자 판단)**. 지운 경로가 다른 핸들러로 새지 않게 하는 규칙이며, 옆 주석에 이유를 적는다. 응답은 주변과 같다(토큰 없으면 401, 있으면 403, Google 호출 0회).
- 대안은 `placeId`에 Google 장소 ID 형식 검사를 더하는 것이다. 이번 범위에는 넣지 않고 앱·백엔드 장소 입력 검증 과제로 남긴다.

- 앱에 남은 미사용 코드(`fetchNearbyPlaces`, `fetchNearestPlace`, `loadNearbyPlaces`)와 `ApiConfig`의 경로 상수는 앱의 "지도 기능 전체 정리" 항목에서 정리한다. 최근접 관련 앱 코드는 백엔드에서 사라졌으므로 그때 함께 지운다.

## 4. 백엔드 구현 방향
- `common/ratelimit`의 `AuthRateLimiter`를 재사용한다. `RateLimitBucket`에 장소 버킷을 더한다: 검색 1분·1시간, 상세 1분·1시간(창마다 하나씩, `minInterval` 없음).
- 여러 창을 한 번에 판정하는 공개 메서드가 필요하다(지금은 `acquire`(한 버킷)와 `acquireSendCode`만 공개). 이름과 형태는 구현자에게 맡긴다. 기존 원자성(모두 허용일 때만 모두 기록)을 지킨다.
- 이름은 인증 전용처럼 보이지만 범용으로 쓰게 된다. 클래스 이름 변경은 하지 않는다 **(구현자 판단, 변경 범위를 줄이기 위해)**. 클래스 주석만 범용임을 밝힌다.
- 판정 위치: 컨트롤러가 `@AuthenticationPrincipal Jwt`에서 `sub`를 꺼내 서비스에 넘기고, `PlaceService`가 클라이언트를 부르기 **전에** 한도를 확인한다(업무 규칙은 서비스, 외부 호출은 `*Client`).
- `SecurityConfig`: `/api/v1/places/nearby`와 `/api/v1/places/nearest`는 `denyAll()`, `/api/v1/places/search`와 `/api/v1/places/{placeId}`는 `authenticated()`로 둔다. 기존 `/api/v1/places/**` 공개 규칙은 없앤다. 규칙 순서: `nearby`와 `nearest` **두 고정 경로의 차단 규칙을 모두** 상세 경로(`/api/v1/places/{placeId}`)의 인증 규칙보다 먼저 등록한다. 보안 설정은 요청을 허용할지 거절할지만 정하고, 어느 컨트롤러가 처리할지는 MVC가 정한다. 그래서 넓은 인증 규칙이 먼저 오면 로그인 사용자의 요청이 통과해, `/nearby`는 남겨 둔 주변 핸들러에, `/nearest`는 전용 핸들러가 없어 상세 핸들러(`placeId = "nearest"`)에 닿는다. 두 경우 모두 Google 호출이 생길 수 있다. 차단 규칙은 메서드를 지정하지 않아 `GET`·`HEAD` 등 모든 메서드에 적용한다. 남는 장소 경로는 모두 인증 필요.
- 키 상한(버킷당 1만 키)과 가득 찼을 때의 동작은 기존 제한기 규칙을 그대로 따른다.

## 5. 앱 변경 (`tripbler`)
- **검색 중복 제출 방지**: 같은 검색어(정규화 후)와 같은 지도 중심의 요청이 진행 중일 때만 새 요청을 보내지 않는다. 다른 검색어나 다른 위치는 그대로 보낸다. 중심 좌표 비교는 정확히 같은 값 기준 **(구현자 판단: 진행 중에는 사용자가 지도를 옮기지 않으면 값이 같다)**.
- **상세 요청 인증**: `fetchPlaceDetails`가 검색처럼 `Authorization` 헤더를 받고, `MapProvider`는 `runAuthorizedRequest`로 부른다.
  - 최초 `401`에는 기존 흐름대로 토큰을 재발급해 한 번 다시 시도한다.
  - 세션 종료(토큰 삭제·로그아웃)는 재발급 요청에서 Refresh Token이 무효·만료로 확인될 때만 한다(`AuthRepository.isSessionExpiredError`: `INVALID_REFRESH_TOKEN`, `EXPIRED_REFRESH_TOKEN`).
  - `429`, 네트워크 오류, 5xx, 재발급 뒤 다시 받은 401 등 그 밖의 실패는 로그인 상태를 유지하고 상세 카드에 실패를 표시한다.
  - 비로그인·세션 만료 시 안내는 검색과 같은 방식을 따른다.
- **429 표시**: 검색과 상세 모두 서버 `message`("요청이 너무 많습니다. 잠시 후 다시 시도해 주세요.")가 보이는지 확인한다. 429에서 세션이 만료 처리되지 않아야 한다.
- **적용 순서**: 앱이 먼저 상세 요청에 토큰을 보내게 하고, 그다음 백엔드가 상세를 로그인 필수로 바꾼다. 거꾸로 하면 현재 앱의 상세 조회가 401로 깨진다. (개발 단계에서는 두 저장소를 같은 날 고치되, 앱 변경을 먼저 반영한다.)

## 6. 테스트 (완료 조건)
**백엔드**
- 검색: 허용되는 마지막 요청(1분 10번째)은 통과하고 11번째는 429 + `Retry-After`. 1시간 100번째 경계도 같다. 거절된 요청에서 `PlaceClient` 대역 호출 0회.
- 상세: 같은 방식으로 1분 20회, 1시간 200회 경계. 거절 시 클라이언트 호출 0회.
- 사용자 A가 한도에 걸려도 사용자 B는 통과한다. 검색과 상세는 따로 센다.
- 상세: 토큰 없으면 401, 클라이언트 호출 0회.
- 검증 실패(400) 요청은 검색 한도를 차감하지 않는다.
- 주변·최근접 접근 차단(`PlaceControllerSecurityTest`): 두 주소 모두 `GET`과 `HEAD`에서 토큰 없음 → 401, 유효한 토큰 → 403, 서비스·Google 클라이언트 호출 0회. `nearest`는 상세 조회(`getPlaceDetails("nearest")`)도 호출되지 않아야 한다. 기존 `주변_검색은_토큰_없이_호출할_수_있다`, `최근접_조회는_토큰_없이_호출할_수_있다`는 이 기준으로 바꾼다.
- 상세 접근(기준이 다름): 토큰 없음 → 401이고 서비스·클라이언트 호출 0회. **유효한 토큰이면 403이 아니라 상세 핸들러에 도달**해 기존처럼 응답한다(200, 없는 장소면 404). 기존 `상세_조회는_토큰_없이_호출할_수_있다`는 "토큰 없으면 401"과 "토큰이 있으면 200" 두 테스트로 바꾼다.
- `PlaceControllerTest`의 기존 상세 테스트(없는 장소 → 404 `RESOURCE_NOT_FOUND`, 지금은 토큰 없이 요청)는 유지하고 요청에 `.with(jwt())`를 더해 장소의 404를 계속 검증한다.
- 유지하는 테스트: 주변 장소를 가져오는 서비스·Google 클라이언트 테스트(`GooglePlacesClientTest`의 주변 검색 요청·응답·오류 테스트 등)는 그대로 두고 통과해야 한다.
- 정리하는 테스트: 최근접만 다루는 서비스·클라이언트·컨트롤러 테스트는 코드와 함께 지운다. `PlaceControllerTest`의 주변 조회 컨트롤러 테스트(파라미터 검증·응답 형식)는 차단 뒤 HTTP로 닿을 수 없으므로 지운다 **(구현자 판단)**. 다시 열 때 git 기록에서 되살린다는 내용을 차단 규칙 주석에 함께 적는다.
- 429 응답이 `ErrorResponse` 형식을 지킨다.

**앱**
- 같은 검색어·같은 중심의 요청이 진행 중이면 다시 보내지 않고, 다른 검색어나 다른 중심이면 보낸다.
- 상세 요청에 `Authorization`이 붙고, 401이면 재발급 후 다시 시도한다.
- 검색·상세의 429에서 서버 메시지가 보이고 로그인 상태가 유지된다.

## 7. 범위 밖
- 서버 결과 캐시.
- 앱 30분 상세 캐시의 약관 검토(별도 과제).
- Google Cloud 쿼터·예산 알림 설정(콘솔 작업).
- 실제 Google 호출 검증(테스트는 대역 사용).

## 8. 점검
- 인증·접근 권한(`SecurityConfig`)을 바꾸므로 구현 후 `code-inspector`와 `security-reviewer`로 점검한다. 앱은 앱 저장소 규칙에 따른다.
