# 공개 인증 API 남용 방지 설계

작성일: 2026-11-12 · 상태: 확정(사용자 승인)

표기: **(구현자 판단)**은 대화에서 정하지 않아 설계자가 정한 부분이다. 표시가 없는 부분은 사용자 결정이거나 사용자가 전달한 검토 의견을 반영한 것이다.

## 배경과 목적
- 아이디 찾기·비밀번호 재설정 인증코드는 6자리 숫자, 유효 5분이다.
- 오답이면 `increaseAttemptCount()`를 부른 직후 `BusinessException`을 던지는데, 서비스가 클래스 단위 `@Transactional`이라 롤백되어 횟수가 저장되지 않는다. 상한 검사도 없다. 5분 안에 코드 전체를 대입할 수 있다.
  - `auth/service/FindIdVerificationService.java` 116행 부근, `auth/service/PasswordResetVerificationService.java` 153행 부근.
- `/api/v1/auth/**`와 회원가입에는 요청 횟수 제한이 없고, 인증 메일에는 재발송 간격 제한이 없다.
- 환경: 개발 단계, 서버 한 대, 프록시 없음, 사용자 한 명.

목표: 인증코드 대입을 막고, 공개 인증 API와 인증 메일 발송의 남용을 막는다. 계정 존재 여부가 새로 드러나지 않아야 한다.

## 1. 인증코드 오답 제한 (DB 저장, 최우선)
아이디 찾기와 비밀번호 재설정 모두에 적용한다.

- 검증 대상 인증코드 행을 `PESSIMISTIC_WRITE`로 잠근 상태에서, 한 트랜잭션 안에서 다음을 끝낸다.
  1. 사용 여부, 만료, 폐기(오답 5회 이상) 확인
  2. 코드 비교
  3. 성공 또는 실패 기록
- 오답이면 실패 결과를 정상 커밋한 뒤 트랜잭션 바깥에서 400 오류로 변환한다. `BusinessException` 전체의 롤백을 해제하는 방식(`noRollbackFor`)은 쓰지 않는다.
- 같은 코드를 5번 틀리면 폐기한다.
  - 5번째 오답의 응답부터 "새 인증코드를 요청해 주세요" 오류 코드(400)를 보낸다.
  - 폐기 뒤에는 정답도 거절한다.
- 이미 사용했거나 폐기된 코드에 대한 요청은 횟수를 올리지 않는다.
- 동시 요청: 다섯 번째 오답이 먼저 확정되면 뒤의 정답은 거절한다.
- 기존 `attempt_count` 열을 쓴다. 폐기 상태는 `attempt_count >= 5`로 판단하고 새 열을 만들지 않는다 **(구현자 판단)**.
- 새 오류 코드는 기존 이름 규칙에 맞춰 흐름별로 둔다(예: `FIND_ID_VERIFICATION_ATTEMPTS_EXCEEDED`, `PASSWORD_RESET_VERIFICATION_ATTEMPTS_EXCEEDED`) **(구현자 판단)**.

## 2. 인증 메일 발송 제한 (메모리 저장)
대상: `POST /api/v1/auth/find-id/send-code`, `POST /api/v1/auth/password-reset/send-code`.

**세는 기준**
- 입력 이메일의 앞뒤 공백을 지우고 소문자로 바꾼 값.
- 두 흐름의 발송량을 합산한다.

**시간 규칙**
- 같은 이메일은 마지막 발송 뒤 60초가 지나야 다시 보낼 수 있다.
- 최근 60분 동안 최대 5통.
- 허용 시각과 정확히 같은 시각의 요청은 통과한다.
- `Retry-After`는 남은 시간을 초 단위로 올림한다.

**계정 존재 숨기기**
- 발송 자리는 계정 조회 **전에** 확보한다.
- 한도 안이면 가입 여부·정보 일치 여부·메일 발송 성공 여부와 상관없이 같은 접수 응답(현재와 같은 `204`)을 준다.
- 한도를 넘으면 같은 `429`를 준다.

**발송 실패**
- 새 코드 발급(기존 코드 삭제 + 새 코드 저장)을 롤백해 이전 코드를 유지한다.
- 발송 한도는 되돌리지 않고 차감된 채로 둔다.
- 응답은 접수 응답과 같고, 실패는 서버 로그에만 남긴다.
- 방식: 발급 트랜잭션 안에서 발송 실패 예외를 다시 던져 롤백하고, 트랜잭션 바깥에서 접수 응답으로 바꾼다 **(구현자 판단)**.

**동시 요청**
- 한도 확인과 자리 확보를 원자적으로 처리한다. 동시에 두 번 요청해도 메일은 한 통만 나간다.

## 3. IP별 요청 횟수 제한 (메모리 저장)
- IP는 `HttpServletRequest.getRemoteAddr()`만 쓴다. `X-Forwarded-For`는 믿지 않는다.
- 모든 한도는 최근 N분 슬라이딩 기준이다 **(구현자 판단)**.

| 묶음 | 경로 | 한도 | 처리 위치 |
| --- | --- | --- | --- |
| 로그인 | `POST /api/v1/auth/login` | 1분 10번 | 인터셉터 |
| 메일 발송 | 두 `send-code` | 10분 5번, 접수된 요청만 셈 | 서비스 앞, 이메일 한도와 함께 판정 |
| 복구·가입 | 두 `verify-code`, `POST /api/v1/auth/password-reset`, `POST /api/v1/users`, `GET /api/v1/users/check-login-id` | 1분 30번 **(구현자 판단)** | 인터셉터 |
| 세션 | `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout` | 1분 60번, 다른 묶음과 따로 셈 **(구현자 판단)** | 인터셉터 |

- 인터셉터 묶음은 인터셉터에 도달한 요청을 결과(성공·실패)와 상관없이 센다 **(구현자 판단)**.
- `check-login-id`는 아이디 대량 확인에 쓰일 수 있어 포함한다 **(구현자 판단)**.

**`send-code`의 IP·이메일 함께 판정**
- 두 한도를 한 번에 확인하고, 둘 다 허용될 때만 두 자리를 함께 확보한다.
- 한쪽 한도로 거절된 요청은 다른 쪽 횟수를 차감하지 않는다.
- 둘 다 걸리면 `Retry-After`는 긴 쪽이다.

## 4. 메모리 키 상한
- 한도 종류별로 키 최대 10,000개 **(구현자 판단)**.
- 가득 차면 만료된 키부터 지운다. 만료 키 정리는 접근 시와 상한 도달 시에 하고 별도 스케줄러는 두지 않는다 **(구현자 판단)**.
- 그래도 가득 차 있으면 기존 키의 제한은 유지하고, 새 키의 요청은 `429`로 거절하며 경고 로그를 남긴다 **(구현자 판단)**.
  - 이때 `Retry-After`는 기존 키 중 가장 먼저 만료되는 키까지 남은 초(올림)다.

## 5. 공통
- 일시 차단: 새 오류 코드 `TOO_MANY_REQUESTS`(429) + `Retry-After` 헤더, 기존 `ErrorResponse` 형식(`timestamp`, `status`, `code`, `message`, `path`).
- `TOO_MANY_REQUESTS`는 앱이 세션 만료로 보는 `INVALID_REFRESH_TOKEN`·`EXPIRED_REFRESH_TOKEN`과 다르므로 토큰 갱신이 429를 받아도 앱은 로그아웃하지 않는다(`tripbler/lib/repositories/auth/auth_repository.dart`의 `isSessionExpiredError`).
- IP 인터셉터는 `WebConfig`에 등록한다 **(구현자 판단)**.
- 시간은 주입한 `Clock`으로 계산한다.
- 새 라이브러리는 추가하지 않는다.

## 6. 테스트 (완료 조건)
**인증코드 — 실제 DB, 요청마다 별도 트랜잭션, 두 흐름 모두**
- 4번 틀린 뒤 정답은 성공한다.
- 5번 틀린 뒤에는 정답도 거절된다.
- 실패 응답 뒤에도 DB에 횟수가 남아 있다.
- 5번째 오답의 응답 자체가 "새 코드 요청" 오류 코드다.
- 새 코드를 발급하면 이전 코드는 거절되고 새 코드는 정상 사용된다.
- 이미 사용했거나 폐기된 코드는 횟수가 오르지 않는다.

**동시성 — 실제 DB, 여러 스레드**
- 오답 두 개가 동시에 들어와도 횟수가 정확히 2 늘어난다.
- 다섯 번째 오답과 정답이 겹칠 때 오답이 먼저 확정되면 정답은 거절되고, 정답이 먼저 확정되면 성공한다. 어느 쪽이든 횟수는 5를 넘지 않는다.

**메일 발송**
- 60초·60분 경계에서 정확히 막히고, 허용 시각과 같은 시각에는 통과한다.
- 두 흐름의 발송량이 합산된다.
- 동시에 두 번 요청해도 메일은 한 통이다.
- 가입된 이메일의 발송 실패와 미가입 이메일 요청의 HTTP 상태·본문·남은 한도가 같다.
- 발송이 실패해도 이전 코드는 쓸 수 있고, 새 코드는 DB에 남지 않으며, 한도는 1 차감된다.

**IP 제한**
- 허용되는 마지막 요청은 통과하고, 바로 다음 요청은 429와 `Retry-After`를 받는다.
- `send-code`에서 두 한도에 모두 걸리면 긴 쪽 시간을 준다.
- 한쪽 한도로 거절된 요청은 다른 쪽 남은 횟수를 줄이지 않는다.
- `refresh`는 다른 묶음과 따로 센다.

**키 상한**
- 가득 찬 상태에서 새 키는 429를 받고, `Retry-After`는 가장 먼저 만료되는 기존 키까지 남은 시간이다. 그 시각이 지나면 새 키 요청이 통과한다.

**컨트롤러**
- 429 응답이 `ErrorResponse` 형식을 지킨다.

실제 DB 테스트는 `SPRING_DATASOURCE_PASSWORD` 환경 변수를 넘겨 실행한다. 외부 메일 발송은 대역으로 대체한다.

## 7. 범위 밖
- 계정 잠금(남이 일부러 틀려 계정 주인을 잠글 수 있음).
- 메일을 동기로 보내 생기는 응답 시간 차이로 인한 계정 존재 추측(별도 과제).
- 여러 서버, 프록시 구성.

## 8. 후속 작업과 점검
- 앱(`tripbler`, 별도 진행): 토큰 갱신 429에도 저장 토큰·로그인 상태 유지 회귀 테스트 1건. 로그인·아이디 찾기·비밀번호 재설정 화면의 서버 메시지 표시 확인. 앱은 서버 `message`를 기본 문구보다 우선해 보여 주고, `Retry-After`는 읽지 않는다.
- 구현 후 `code-inspector`와 `security-reviewer`로 점검한다(인증, 계정 복구, `WebConfig` 변경).

## 9. 구현 후 변경
점검(`code-inspector`, `security-reviewer`) 결과에 따라 구현 뒤 바꾼 내용이다. 위 본문은 처음 설계 그대로 두었다.

- **인증코드 실패 응답 통합(2026-11-12, 사용자 결정, security-reviewer H-1)**: 인증 레코드가 없으면 몇 번을 틀려도 `INVALID_*`만, 레코드가 있으면 5번째 오답부터 `*_ATTEMPTS_EXCEEDED`가 나가서, 발송 1회와 오답 5회로 이메일이 연동 계정인지(재설정은 아이디와 이메일이 같은 계정인지) 알 수 있었다. 만료 코드(`EXPIRED_*`)도 5분을 기다리면 같은 정보를 줬다. 그래서 `verify-code`의 모든 실패를 흐름별 코드 하나(`INVALID_FIND_ID_VERIFICATION_CODE`, `INVALID_PASSWORD_RESET_VERIFICATION_CODE`, 400)로 응답하고, 메시지는 "인증코드가 올바르지 않거나 만료되었습니다. 새 인증코드를 요청해 주세요."로 바꿨다. `*_ATTEMPTS_EXCEEDED`, `EXPIRED_*_VERIFICATION_CODE`는 지웠다. 행 잠금, 오답 기록 커밋, 5회 폐기, 사용·만료·폐기 코드의 횟수 미증가 등 내부 동작은 그대로다. 앱은 이 코드로 분기하지 않고 서버 메시지만 보여 주므로 고치지 않는다.
- **HEAD 요청 정규화**: Spring MVC는 `@GetMapping` 핸들러로 `HEAD`도 처리하는데, 인터셉터는 `GET`만 세서 `HEAD /api/v1/users/check-login-id`로 제한을 피할 수 있었다. 판정할 때 `HEAD`를 `GET`으로 바꿔 같은 한도로 센다.
- **제한기 필수 등록**: `WebConfig`가 `ObjectProvider.ifAvailable`로 제한기를 찾아, 빈이 없으면 오류 없이 제한이 꺼진 채 기동했다(fail-open). 이제 `AuthRateLimiter`는 컴포넌트 스캔 대신 `WebConfig`의 `@Import`로만 등록하고 `WebConfig`가 직접 주입받아 인터셉터를 항상 붙인다. 제한기를 만들 수 없으면 기동이 실패한다. `@WebMvcTest` 슬라이스에도 실제 제한기와 인터셉터가 붙는다.
